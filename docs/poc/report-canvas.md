## 結論（最重要）: スケール不変レンダリングは「条件付きで成立する」

論理座標系（幅1000単位）で描画命令を書き、ctx.setTransform(k,0,0,k,0,0) でスケールするだけで、写真合成部分・フレーム・罫線は**ピクセル完全一致**。差分が出るのは**テキストの描画（アンチエイリアシング/ヒンティング）のみ**で、影響範囲は限定的。

実測（test1_scale_invariance.js、プレビュー幅800px vs 書き出し幅6000px、書き出しを800pxへ縮小して比較。1000x1250論理キャンバス＝4:5想定）:

| 比較対象 | 総ピクセル数 | 差分ピクセル数(閾値0.1) | 差分率 | 平均チャンネル差 | 最大チャンネル差 |
|---|---|---|---|---|---|
| 合成画像全体（写真＋フレーム＋文字） | 800,000 | 1,272 | 0.159% | 0.28/255 | 141/255 |
| 文字キャプション領域のみ（クロップ） | 102,400 | 1,272 | 1.24% | 1.57/255 | 141/255 |

- 差分ピクセルはすべてキャプション文字の領域（y=880〜936、文字の輪郭部分）に局在。写真領域・背景・罫線・フレーム枠は差分ゼロ（バウンディングボックス解析で確認）。
- 原因は文字のサブピクセル・アンチエイリアシングが、800px描画時のヒンティングと、6000px描画→800pxへの縮小（リサンプリング）とで完全一致しないこと。原理的に避けられない。
- ctx.letterSpacing（Chromiumでサポート、'letterSpacing' in ctx = true）は**スケールに正確に比例**することを実測: 論理幅567.03単位のテキストが、k=0.8で453.63px、k=6で3402.20px → 実測比 7.500000、期待比(6000/800)も7.500000で完全一致。字送りの比例崩れは無し。

**設計への示唆**: 「プレビューと書き出しが完全一致」という要件は、写真・フレーム・グレインについては達成可能。テキストについては「ピクセル完全一致」ではなく「実用上区別できない程度の一致（差分0.16%、平均誤差0.28/255）」が正しい表現。

## Part 2: 巨大キャンバスの限界（実測: Chromium）

test2_canvas_limits.js — 各サイズで canvas.width/height 設定 → getContext('2d') → fillRect全面 → getImageDataで四隅を読み戻し検証。

| サイズ | 総ピクセル数 | getContext | fillRect→読み戻し | 判定 |
|---|---|---|---|---|
| 6000x7500（本アプリ想定, 4:5） | 45,000,000 | 成功 | 正しい色(fill 110ms, read 21.6ms) | OK |
| 6000x4000（原寸） | 24,000,000 | 成功 | 正しい色 | OK |
| 8192x8192 | 67,108,864 | 成功 | 正しい色(fill 854ms) | OK |
| 16384x16384（=2^28ちょうど） | 268,435,456 | 成功 | 正しい色(fill 2370ms, read 118ms) | OK（上限ぎりぎり） |
| 16385x16384（2^28+16384） | 268,451,840 | 成功（trueが返る） | [0,0,0,0]＝黒/透明。fillRect/getImageDataとも0ms＝実質何もしていない | 黙って失敗 |
| 32767x1 / 32768x1 | — | 成功 | 正しい色 | OK |
| 65535x1 | 65,535 | 成功 | 正しい色 | OK |
| 65536x1 | 65,536 | 成功 | [0,0,0,0]＝黙って失敗 | NG |
| 20,000x20,000（400MP） | 400,000,000 | 成功 | [0,0,0,0] | NG |
| 100,000x100,000 | 10,000,000,000 | 成功 | [0,0,0,0] | NG |

**実測で判明した上限（Chromium 141, Linux）**:
- **総ピクセル数（面積）上限 = 268,435,456 px = 2^28**。1pxでも超えると失敗。6000x7500(4500万px)は上限の約1/6で余裕がある。
- **単一辺の上限は65535px（2^16-1）以下、65536pxで失敗**（面積が小さくても辺長だけで弾かれる）。
- **エラーの出方**: width/heightへの代入もgetContext('2d')もfillRectも例外を投げない。**しかし実際には何も描画されておらず、getImageDataで読むと透明黒(0,0,0,0)が返る＝「黙って失敗」する。** 例外ベースのエラーハンドリングでは検知不可能。
- **検知方法（実証済み）**: 生成直後に1x1pxをfillRect→getImageData(0,0,1,1)で読み戻し、期待した色が返るか確認するガードが有効。

### メモリ・処理時間（実測: 6000x7500に実写真を合成描画した場合）

performance.memory（JSヒープ）は**信頼できない**ことが判明: 複数回測定してもUsed/Totalが常に10000000（1000万）ちょうどに丸められる。Chromiumのフィンガープリンティング対策による量子化・ノイズ付与のためで、実際のキャンバス裏メモリを反映しない。

そこでChromiumプロセス群のRSS（実メモリ常駐量）を/proc/<pid>/statusから直接集計（test2b_rss_memory.js）:

| 状態 | 合計RSS | ベースラインからの増分 |
|---|---|---|
| Chromiumプロセス群のベースライン（6プロセス） | 355.1 MB | — |
| ＋6000x7500の写真合成キャンバス1枚生成後 | 772.3 MB | +417.2 MB |
| ＋さらに16384x16384（上限ぎりぎり）のキャンバスを追加生成後 | 1917.5 MB | +1145.2 MB |

- 6000x7500（4500万px）1枚だけで**+417MBの実メモリ**を消費した（生ピクセルバッファ計算値180MB=6000×7500×4byteに対し、デコード済みJPEGソース画像バッファやダブルバッファリング、GPU側テクスチャ等のオーバーヘッドを含めると妥当）。
- モバイル端末（特にiOS Safari）では重大な制約になり得る。フレーム編集中に複数の中間キャンバスを同時保持しない設計が重要。

### canvas.toBlob() の所要時間とファイルサイズ（実測: 6000x7500、実写真合成後）

| フォーマット | 所要時間 | ファイルサイズ |
|---|---|---|
| PNG | 132 ms | 1,053,869 bytes (1.03 MB) |
| JPEG quality=0.92 | 249.6 ms | 638,156 bytes (623 KB) |
| JPEG quality=0.95 | 246 ms | 787,828 bytes (770 KB, +23.5%対0.92) |
| WebP quality=0.92 | 3091.4 ms | 177,172 bytes (173 KB) |

- WebPは最も小さいファイルを作るが、**エンコードに約3.1秒**かかり、PNG/JPEGの12〜23倍遅い。45MPキャンバスでWebPをデフォルトにすると数秒間のフリーズ感が出る（Web Worker化やプログレス表示が必須）。
- JPEGはquality 0.92→0.95で+23.5%サイズ増、時間はほぼ変わらず。

## Part 3: 書き出しとEXIF（実測）

- 元画像mirrorless_landscape.jpgのEXIF: Make=FUJIFILM, Model=X-M5, DateTimeOriginal=2026:09:20 17:42:11, GPS等含め0th=6項目/Exif=9項目/GPS=4項目 確認。no_exif.jpgはEXIFフィールド0件、rotated_orient6.jpgはOrientation=6、iphone_portrait.jpgはOrientation=1で共に15項目。
- **canvas.toBlob('image/jpeg')で書き出したJPEGはEXIFが完全に失われる**（フィールド数0を実測で確認）。
- **piexifjsでの書き戻しは実測で成功**: 元画像のEXIF dict（サムネイル除去）をpiexif.dump→piexif.insertでCanvas書き出し後のJPEGバイナリに挿入。再度piexif.loadで読み戻し、Make/Model/DateTimeOriginalが元と一致することを確認。ファイルサイズ増加は+414byte（638,156→638,570）と軽微。
  - 制約: PNG/WebPにはEXIF埋め込みの標準機構がなく、piexifjsもJPEG専用。**EXIFを保持したいならJPEG書き出しを選ぶ必要がある。**

## Part 4: 保存・共有（実測はChromiumのみ、iOS Safariは未実測）

| 機能 | 実測結果 |
|---|---|
| <a download> + Blob URL | **成功**。Playwrightのdownloadイベントが発火し、suggestedFilename='test-frame.png'、保存後のファイルサイズはCanvas由来のPNGと一致(42,919 bytes)。 |
| navigator.share({files}) | **この環境ではnavigator.share関数自体が存在しない**（typeof navigator.share !== 'function'）。isSecureContextはtrue（http://localhostは特別扱いでsecure扱い）なので、原因はセキュアコンテキストではなくプラットフォーム側の未実装。LinuxデスクトップのChromiumはOSレベルの共有シート統合を持たないため、Web Share APIが一般に無効というのはよく知られた挙動で、今回の結果と整合する。 |

**設計への示唆**: <a download>は堅牢に動作する。navigator.shareはプラットフォーム依存が強く、フォールバック必須（typeof navigator.share === 'function'を確認し、無ければ<a download>に自動フォールバックする設計）。

### iOS Safariについて（**未実測・調査ベース**、実機検証は不可のため）
- iOS SafariのWeb Share Level 2（files付きnavigator.share）はiOS 15以降でサポートされているとされるが、**ユーザー操作に直接紐づくハンドラ内から同期的に呼び出す必要がある**という制約が広く報告されている（非同期処理を挟むとNotAllowedErrorになりやすい、という報告がある）。
- 「長押しでカメラロールに保存」は、**<img>タグとして表示されている画像であれば有効**というのが一般的な理解。**生の<canvas>要素を直接長押ししても保存メニューは出ない**という報告が多く、保存を長押しに頼るなら、書き出し結果を一度canvas.toDataURL()/toBlob()＋<img src=...>として表示し直す必要がある可能性が高い。
- 上記2点はいずれも実機未検証。実装時はiOS実機での動作確認を必須とすべき。

## Part 5: フィルム風グレイン/質感（実測: Chromium、6000x7500）

3手法を実装し実測（test5_grain.js）。

| 手法 | 書き出し時(6000x7500)所要時間 | プレビュー時(800x1000)所要時間 |
|---|---|---|
| A: ImageData直接操作、1デバイスピクセル単位ノイズ | 809.3 ms | 15.9 ms |
| A': ImageData操作だが粒サイズをk倍に拡大したセル単位ノイズ | 562.9 ms | 22.0 ms |
| B: 小タイルノイズ画像をcreatePattern+globalCompositeOperation='overlay'で全面に敷く | 1.7 ms | 0.2 ms |
| C: SVG feTurbulenceフィルタを<img>化してdrawImage | 4.4 ms（画像デコード込み） | 1.7 ms |

- **ImageDataを1px単位でいじる方式は45MPで約0.8秒かかり、パターン/SVG方式（数ms）より2〜3桁遅い。** UIのレスポンスを考えるとパターンタイルかSVGフィルタを採用すべき。

### プレビューと書き出しで粒の見た目が一致するか（本要件の核心）— 実測で「破綻する」ことを確認

自己相関的な指標（水平方向に隣り合う画素の平均絶対差=avgLag1Diff。値が大きいほど「毎ピクセル値が変わる＝細かい粒」、小さいほど「なめらか＝粗い/薄い粒」）で、同じ論理領域を(1)プレビューでネイティブ描画, (2)書き出し解像度でネイティブ描画, (3)書き出しをプレビューと同じ表示サイズに縮小、の3条件で比較。

**方式A（1デバイスピクセル＝1粒、スケール非対応）:**

| 条件 | avgLag1Diff |
|---|---|
| プレビュー(800px)でネイティブ描画 | 13.34 |
| 書き出し(6000px)でネイティブ解像度のまま計測 | 13.33（＝統計的に同じノイズ強度） |
| 書き出しをプレビューと同じ表示サイズに縮小 | 1.50 |

→ プレビューで見えている粒の強さを100とすると、実際に書き出された6000x7500画像を同じ倍率で表示・縮小した際の粒の強さは**約11%まで激減**する（13.34→1.50、約8.9倍の低下）。「1粒＝1物理ピクセル」で実装すると、書き出し解像度がプレビューの7.5倍あるため、粒が細かすぎて縮小時にほぼ平均化されて消えてしまう。**プレビューで見た質感と、実際に書き出された画像を通常の閲覧倍率で見た質感が一致しない＝最重要要件が破綻する典型例。**

**方式A'（粒のセルサイズをk倍にスケールし、常に論理1単位あたりの粒個数を一定に保つ）:**

| 条件 | avgLag1Diff |
|---|---|
| プレビュー(800px)でネイティブ描画 | 13.25 |
| 書き出しをプレビューと同じ表示サイズに縮小 | 6.15 |

→ 低下幅は13.25→6.15（約2.15倍の低下）に大きく改善するが、**完全には一致しない**。残る差は整数デバイスピクセルへの丸め誤差や、縮小時のフィルタによるボックスセルの角のぼやけなど。

**設計への示唆（重要な制約）**:
- グレイン・粒子系の質感は、**必ず「論理座標系に対する相対サイズ」でパラメータ化し、実際の描画時にキャンバスの k = 出力px幅 / 論理px幅 を掛けて粒サイズをスケールしなければならない**。固定px単位で実装すると、プレビューと書き出しで見た目が全く別物になる。
- パターン/SVGタイル方式を採用する場合も、タイルの生成サイズ自体をk倍してから敷く必要がある（本PoCのgrainPatternTileはtileLogicalPx * kでこれを実装し、実測で機能を確認済み）。
- 完全な一致は困難（縮小フィルタの影響が残る）なので、「見た目が近い」レベルを目標にするのが現実的。

## 総括: 設計に影響する制約（箇条書き）

1. **スケール不変レンダリングは条件付きで成立**。写真・フレーム・グレイン(スケール対応実装なら)はピクセル完全一致に近い（差分0.16%未満）。テキストのみアンチエイリアシング起因の微小な差（差分1.24%、平均誤差0.28/255）が残るが、視覚的には実用上問題ないレベル。
2. **キャンバスサイズには実測でハードリミットがある**: 面積上限 2^28=268,435,456px、辺長上限 65,535px未満。6000x7500(4500万px)はこの上限の1/6程度で余裕があるが、より大きな解像度に対応する場合は要注意。
3. **上限超過は例外を投げず「黙って失敗」する**（getImageDataが全て0を返す）。**キャンバス生成直後に1pxの書き込み→読み戻しで検証するガード処理が必須**。
4. **performance.memoryは信頼できない**（Chromiumが値を1000万単位に丸める）。実メモリはOSレベル(RSS)で計測する必要があり、実測では45MPキャンバス1枚で+417MBの実メモリを消費した。モバイル、特にiOS Safariのメモリ制約下では複数の中間キャンバスを同時に持たない設計（都度destroy、使い回し）が重要。
5. **WebPエンコードは高圧縮だが激遅い**（45MPで3.1秒、PNG/JPEGの12〜23倍）。書き出しフォーマットにWebPを使うならWeb Worker化やプログレス表示が必要。
6. **CanvasのJPEG書き出しはEXIFを完全に失う**。撮影情報を残したいならpiexifjs等で元画像のEXIFを書き出し後JPEGに再注入する後処理が必要（実測で成功、サイズ増加は数百byte程度と軽微）。PNG/WebPにはこの手段がない。
7. **<a download>はChromiumで堅牢に動作**するが、**navigator.shareはプラットフォーム依存が強く、必ずフィーチャーディテクトとフォールバックが必要**（今回の検証環境では関数自体が存在しなかった）。iOS Safariでの実際の挙動は未実測。
8. **グレイン/質感は「論理座標系に対する相対サイズ」で必ず設計しないと、プレビューと書き出しの一致という最重要要件が壊れる**。1粒＝1物理ピクセルの素朴な実装では、書き出し解像度がプレビューの7.5倍ある場合、書き出し画像を同倍率で見たときの粒の強さがプレビューの約11%まで激減することを実測で確認した。粒サイズをk倍することで改善はするが完全一致はしない。
9. **グレイン実装はアルゴリズム選択が性能に直結**: ImageData直接操作は45MPで約0.8秒かかるのに対し、パターンタイル/SVGフィルタ方式は数msで完了する。UIレスポンス重視ならパターン/SVG方式を採用すべき。
