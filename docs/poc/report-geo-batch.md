# PoC実測レポート: 撮影地表示（GPS→地名）と複数枚一括処理

実行環境: Node v22.22.2 / Chromium 141 headless / 4vCPU 15GB RAM
作業一式: `scratchpad/poc/geo-batch/`

凡例:「実測」= 実際に実行して得た数値。「調査ベース（未実測）」= この環境では実行確認できなかったもの。

## 前提となる重要な制約（実測で判明）

このサンドボックスのアウトバウンドプロキシはホスト単位の許可リスト制で、
`nominatim.openstreetmap.org` / `*.gsi.go.jp` / `download.geonames.org` / `api.opencagedata.com` /
`api.mapbox.com` へは **curl でも Chromium の fetch でも接続不可**（プロキシが CONNECT を403で拒否）。
github.com(raw含む) と npm registry のみ到達可能。
そのため**オンライン逆ジオコーディングAPIの実地検証（CORS・実レスポンス・レイテンシ）は不可**だった。
以下 A-2 はすべて調査ベース。**本番投入前に実機・実ブラウザでの再検証が必須**。

## A. 撮影地の表示（GPS→地名）

### A-1. オフライン方式（同梱データ）— 実測

- **Geolonia住所データ**（`geolonia/japanese-addresses`）を GitHub raw 経由で実ダウンロード
  （`data/latest.csv`、277,543件、**実測 51,865,104 bytes**）。ライセンスは README を読み
  **CC BY 4.0**（商用可・再配布可、要出典表示）と確認。
- 市区町村コード単位で緯度経度を平均し、**1,894市区町村の centroid データを実際に生成**
  （ビルド1,261ms、アプリ実行時には不要な前処理）。
  - CSV: 生 100,764 B → **gzip 37,433 B (36.6KB)**
  - JSON(コンパクト配列): 生 100,743 B → **gzip 32,905 B (32.1KB)**
  - → 日本全市区町村を**約33KB(gzip)**で同梱できることを実測確認。
- **最近傍探索（Haversine、1,894件ブルートフォース）を実行**:
  - テスト座標 (34.3853, 132.4553) → 最近傍 = **「広島県 広島市中区」**（距離0.38km）
  - 平均探索時間(1,000回): **0.0898ms/回**
  - **精度の注記**: centroid 最近傍法はポリゴン境界を見ないため、**行政境界付近で隣接自治体に
    誤帰属しうる**。「だいたいの撮影地」なら実用上問題ないが、正確な市区町村名を謳うなら要検討。
- **世界対応時のサイズ（実測）**: npm `all-the-cities`（GeoNames 由来、パッケージMIT / データ CC BY 4.0）:
  - 全135,233件: gzip **1.92MB**
  - 人口≥15,000相当 24,323件: gzip **477,230 B (0.47MB)**
  - 人口≥5,000相当 49,025件: gzip **924,469 B (0.88MB)**
  - → 世界対応にすると +0.5MB 程度。日本専用(33KB)と桁違い。

### A-2. オンライン方式 — 調査ベース（未実測）

- **Nominatim**: 規約上 **1req/秒が上限**、User-Agent/Referer 必須、大量利用は禁止で自前ホスティング推奨。
  ODbL のため **「© OpenStreetMap contributors」の出典表示が必須**（表示すれば商用可）。
  公開デモは一般に CORS 対応とされるが本環境では未確認。
- **国土地理院 逆ジオコーディングAPI**: 正式ドキュメント・SLA が薄く、CORS 対応も不確実。採用前に実機検証必須。
- **バッチ処理との相性**: レート制限がある場合、30枚を逐次問い合わせると30秒以上かかりうる上、
  設計原則にも反する。バッチ向きではない。

### A-3. 比較表と結論

| 軸 | オフライン同梱(市区町村centroid) | オンラインAPI |
|---|---|---|
| サイズ | 実測 約33KB gzip(日本のみ)／世界対応+0.5MB | 追加バンドル0、通信必須 |
| 精度 | 市区町村レベル、境界付近で誤帰属あり(実測確認) | 番地・施設レベル(調査ベース) |
| プライバシー | 写真も GPS 座標も一切外部に出ない。原則と完全整合 | **GPS座標を第三者サーバーに送信**。位置情報単体でも自宅等を特定しうる |
| 規約 | CC BY4.0(出典表示のみ)、レート制限なし、オフライン動作可 | Nominatim は1req/秒・出典義務・大量利用禁止(調査ベース) |

**結論**: オフライン同梱方式を第一選択として推奨。オンラインAPIは精度で勝るが「座標を外部に渡す」代償を伴う。
採用するなら既定オフの明示的オプトインを推奨。

## B. 複数枚の一括処理

### B-1. メモリ（実測、Chromium上）

**Phase A（同時保持）**: count=1 で RSS 819.7MB → count=50 で 5,737.7MB。1枚あたり **約100.4MB** 増加
（生ピクセル91.55MBにほぼ一致）。**`performance.memory.usedJSHeapSize` は終始0.8MB前後で変化なし**
＝ Canvas のピクセルデータはこの指標に現れない重要な落とし穴。

**Phase B（逐次処理: load→draw→encode→即破棄、100枚）**:
baseline 711.3MB → 10枚後 1,307.8MB → 30枚後 1,333.5MB → 50枚後 1,357.9MB → 100枚後 1,417.2MB（ほぼ横ばい）。

**帰結**: 30枚同時プレビュー等のUIは 100MB×30≈3GB となり、モバイル実機
（iOS Safari のタブメモリ上限は一般に1.5〜2GB程度と言われる＝**調査ベース・未実測**）ではクラッシュしうる。
**フル解像度処理は必ず逐次実行し、都度破棄する設計が必須**。

### B-2. 所要時間（実測）

load→draw→JPEG encode(q0.9) を8回連続計測（warm平均、初回除く）:
- mirrorless(6000x4000, 24MP): load146.3 + draw325.5 + encode135.7 = **607.5ms/枚 → 30枚で約18.2秒**
- iphone(3024x4032, 12MP): load61.0 + draw85.5 + encode74.4 = **220.9ms/枚 → 30枚で約6.6秒**

別途、30枚(6000x4000、キャプション描画込み)を実際に連続処理 → **実測9.6〜12.5秒**。
**結論: 24MP級30枚のメインスレッド逐次処理はおおむね10〜20秒**、12MP なら6〜7秒。

### B-3. UIの凍結対策: Web Worker + OffscreenCanvas（実測）

Worker 内で OffscreenCanvas 生成 → drawImage → fillText →
**FontFace API で Noto Sans JP(woff2) を読み込み日本語キャプション描画** → convertToBlob:
- デフォルトフォント fillText: **成功**
- **Worker内 FontFace API による日本語Webフォント読み込み・描画: 成功**
  （Worker に document は無いため DOM の @font-face は使えないが、`FontFace` コンストラクタ +
  `self.fonts.add()` で完全動作。実装上の重要ポイント）
- 非ブロック検証: rAF ハートビートを回しながら Worker 処理 → 1枚処理中(1,373ms)に82回、
  5枚並行処理中(4,185ms)に251回進行（≈60fps相当）。**メインスレッドは全く止まっていない**。

### B-4. 一括保存（実測＋一部調査ベース）

30枚(6000x4000、キャプション付きJPEG q0.9)を実生成: 合計 **実測約7.60MB**（平均259.4KB/枚）

- **(a) ZIP化(fflate)**: `zipSync`(level6) で30ファイル → **271〜274ms**、出力約0.89MB。
  ただし**このZIPサイズは過小評価**。テスト画像は合成グラデーションで DEFLATE が効きやすく、
  level0 では入力と同じ7.60MBになることを確認済み。**実写真ではZIP化してもサイズはほぼ変わらない**。
  処理時間(271ms)自体はボトルネックにならない。
- **(b) 連続 `<a download>`**: 30個を間隔なしで click した結果、**検知された download イベントは30個中10個のみ**
  （5秒待っても増えず）。Chromium の自動連続ダウンロード保護を実測確認。
  **30枚を `<a download>` 連打で保存する方式は実用にならない**。
- **(c) `navigator.share({files})`**: この headless Chromium では `navigator.share`/`canShare` とも
  **未サポート(false)**。Linux headless が OS 共有シート統合を持たないため。
  実機モバイルでは存在し複数ファイル共有に対応する環境が多いとされるが**実機未検証**。
- **(d) File System Access API**: `showSaveFilePicker`/`showDirectoryPicker` は関数として存在するが、
  ユーザージェスチャー必須のため headless では実行検証不可。iOS Safari は非対応（調査ベース）。

**スマホでの現実的な手段（結論）**: **ZIPにまとめて1回のダウンロード/共有に載せる方式を第一候補**。
連続 `<a download>` は10件でブロックされることを実測したため不可。
**iOS Safari 実機検証は一切できておらず、公開前に必ず実機確認が必要**。

## 設計に影響する制約（まとめ）

- 市区町村centroidデータ(gzip約33KB)のオフライン同梱が「サーバーに送らない」原則と両立する最有力策。
  ただし centroid 最近傍法は行政境界付近で誤帰属リスクあり(実測確認)。
- オンライン逆ジオコーディングは GPS 座標という機微情報の外部送信を伴い設計原則と衝突。
  採用するなら明示的オプトイン必須。
- **Canvas保持中の画像メモリは JSヒープ(`performance.memory`)に現れない**(実測)。RSS ベースで考える必要がある。
- 6000x4000 画像は1枚約100MBのメモリを消費(実測)。**フル解像度処理は必ず逐次実行・都度破棄**。
- 30枚の逐次処理(メインスレッド)で**約10〜20秒**(実測)。進捗表示は必須。
- **Web Worker+OffscreenCanvas で処理すればメインスレッドは完全に非ブロック**(実測、60fps相当維持)。
  Worker 内でも FontFace API で日本語Webフォントの読み込み・描画が可能(実測)。
- **`<a download>` の連続実行は10件程度でブロックされる**(実測)。30枚一括保存は ZIP 化必須。
- 実写真では ZIP 化による追加サイズ削減はほとんど期待できない。
- iOS Safari の `navigator.share` 複数ファイル対応、File System Access API 非対応、
  Nominatim/GSI の CORS 実態は、いずれも「調査ベース」の域を出ない。**公開前に実機再検証が必要**。
